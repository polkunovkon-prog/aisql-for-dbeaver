# Безопасность AI SQL for DBeaver

## 1. Цели и модель угроз

Плагин исходит из того, что **языковая модель может ошибиться** (выбрать не ту
таблицу, сгенерировать опасный DDL, «улучшить» данные) и что **данные БД не
должны без необходимости уходить в модель**. Задачи безопасности:

1. ничего не выполнять без явного согласия пользователя (для изменяющих
   операций);
2. не дать модели «случайно» выполнить разрушительный или изменяющий SQL
   там, где это запрещено политикой;
3. не отправлять в модель значения конфиденциальных колонок;
4. оставить проверяемый след обо всех выполненных операциях.

Плагин — **инструмент снижения рисков для добросовестного пользователя**,
а не песочница и не средство защиты от злоумышленника с правами пользователя
ОС/DBeaver. Исключение — **корпоративная политика** (1.5.0): настройки,
зафиксированные администратором, пользователь ослабить не может.

## 2. Слои защиты

Порядок применения (от карточки подтверждения до прав СУБД):

| Слой | Что делает | Где настраивается |
|---|---|---|
| Корпоративная политика | Значения, зафиксированные администратором, перекрывают пользовательские настройки; `tools.disabled` отключает инструменты; fail-closed при недоступной политике | `ai-sql-enterprise.properties` / `-Daisql.enterprise.policy` (см. §8) |
| Подтверждение DBeaver | Карточка Allow/Deny перед вызовом `db_executeSql`, `db_runMacro`, `db_defineMacro`, `db_deleteMacro`, `db_runQuery`, `db_getTableSample` | карточка: ▾ → allow/ask/deny; Preferences → AI → «Инструменты ИИ» |
| `runQuery.strictReadOnly` | `db_runQuery` принимает только read-only операторы, всё остальное — с подсказкой воспользоваться `db_executeSql` | страница плагина |
| Классификатор SQL | На основе парсера DBeaver: SELECT/WITH/SHOW/… — чтение; DML/DDL/DCL/неизвестное — запись. `SELECT … INTO` считается записью. Выбор типа оператора (QUERY/SCRIPT) — тоже классификатор | не настраивается |
| Профили подключений | `READ_ONLY` запрещает любые изменяющие операторы и EXPLAIN ANALYZE; `STANDARD` — обычный режим; `FULL` — без ограничений | `policy.defaultProfile`, `policy.profile.<маска>` |
| `policy.forbidden` | Пользовательские regex-запреты (DROP, TRUNCATE, ALTER SYSTEM…) во всех профилях, кроме FULL | страница плагина / файл |
| Белый список таблиц | `policy.allowedTables.<маска>`: таблицы извлекаются из AST, проверка до выполнения, fail-closed | файл / страница плагина |
| Защита от промпт-инъекций | `injection.mode=off|flag|strict`: в strict SQL с признаками угона модели («ignore previous instructions» и т.п.) блокируется; данные из БД (DDL, образцы) помечаются как «данные, не инструкции» (`toolOutput.fence`) | страница плагина / файл |
| Отключение автокоммита | Перед изменяющими операторами автокоммит выключается: изменения можно откатить | `write.disableAutocommit` |
| Маскирование колонок | Значения колонок по правилам `mask.rules` заменяются до отправки ответа в модель | `mask.enabled`, `mask.rules` |
| Детекция ПДн по значению | email/телефон/карта (Лун)/ИНН/СНИЛС распознаются в любом столбце — защита SELECT * и вычислимых колонок | `mask.detectPII`, `mask.piiReplacement` |
| Правка выделения ИИ | `Ctrl+Alt+E`: замена текста в редакторе — только по явному «Применить» (по умолчанию), один `Ctrl+Z` отменяет; в БД ничего не выполняется | `edit.*` |
| Аудит | Каждая выполняемая функция и результат пишутся в журнал с хеш-цепочкой; события дублируются в SIEM (syslog) | `audit.*`, `audit.syslog.*` |
| Права СУБД | Последний и главный рубеж: плагин не обходит права учётной записи | роли БД |

## 3. Рекомендации по настройке

- Продуктивные подключения — `policy.profile.prod-*=READ_ONLY` (или роль БД
  только на чтение);
- минимальный `policy.forbidden` для прода (при ручной правке файла
  обратные слыши в регулярных выражениях удваиваются: `\\s`):

  ```properties
  policy.forbidden=DROP\\s+TABLE;\nDROP\\s+SCHEMA;\nTRUNCATE\\s+;\nALTER\\s+SYSTEM;\nDROP\\s+DATABASE
  ```

- маскирование секретов: `*.password=***`, `*.token=***`, `*.secret=***`,
  персональные данные — по согласованию (`customers.email=***@***`);
- `audit.redactLiterals=true`, если в запросах встречаются персональные данные
  и нельзя исключить их попадание в журнал;
- подтверждение `db_runQuery` можно оставить только `ASK`, а для доверенных
  read-only сценариев переключить в allow — но помните: `db_runQuery` не умеет
  выполнять изменения (см. `strictReadOnly`).

## 4. Маскирование: что именно скрывается

Правило сопоставляется с колонкой результата по трём именам (сущность,
имя колонки, подпись), а также c именем таблицы (`Globs`-маски, `*`).
Замена выполняется в момент формирования **текстового ответа функции для
модели**; в самом DBeaver кэше результата остаются реальные значения
(пользователь видит их в своей таблице результатов как обычно).

Синтаксис: `таблица.колонка=замена` (в списке — через `;` или перевод строки).
Пропуск замены → `***`. Строки, начинающиеся с `#`, — комментарии.

```properties
mask.enabled=true
mask.rules=*.password=***; *.credit_card=****-****; customers.email=***@***; sakila.customer.*.phone=[телефон]
```

> Обратите внимание: маскирование не защищает от того, что модель **увидит
> сами имена** таблиц и колонок, а также значения незамаскированных колонок.
> Оно лишь предотвращает утечку содержимого указанных колонок.

### 4.1. Детекция ПДн по значению (1.5.0)

`mask.detectPII=true` (по умолчанию) — к ячейкам, **не закрытым** правилами
`mask.rules`, применяется эвристическое распознавание: email; телефон
(РФ и E.164 с «+»); банковская карта (13–19 цифр + алгоритм Луна); ИНН-10/12
и СНИЛС (контрольные суммы). Замена — `mask.piiReplacement` (по умолчанию
`[ПДн]`). Контрольные суммы и форматные требования снижают ложные
срабатывания: даты, идентификаторы и суммы не маскируются. Это страховка
для `SELECT *`, JOIN и вычислимых колонок — полный контроль остаётся за
правилами по именам колонок и правами СУБД.

## 5. Журнал аудита

- Файл: `<workspace>/.metadata/.config/ai-sql-audit.jsonl` (JSON Lines, UTF-8).
- Поля: `ts`, `user`, `host`, `session`, `seq`, `app`, `function`, `decision`,
  `conn`, `category`, `outcome`, `rows`, `bytes`, `ms`, `error`, `detail`,
  `sql`, `prev`, `hash`.
- **Цепочка хешей**: `hash = SHA256(prev + "\n" + строка без поля hash)`,
  у первой строки `prev=genesis`. Любая правка/удаление/вставка строки ломает
  цепочку и обнаруживается. `seq` — номер записи в текущем файле: дыры
  в нумерации выдают удаления даже внутри валидно пересчитанной цепочки.
- `session` — постоянный UUID рабочей области DBeaver
  (файл `ai-sql-session.id`), `host` — имя хоста ОС: корреляция событий
  в SIEM (кто/где/когда/в каком порядке).
- **Экспорт в SIEM** (1.5.0): `audit.syslog.enabled=true`,
  `audit.syslog.host`, `audit.syslog.port` (514), `audit.syslog.facility`
  (16=local0), `audit.syslog.appname` (aisql) — каждая запись дублируется
  UDP-датаграммой RFC 5424-подобного вида
  `<PRI>TIMESTAMP HOST APP PID MSG`, где MSG — JSON события с хешем.
  Отказы/ошибки уходят с severity warning, прочее — informational.
  Проверьте приём кнопкой «Тест: отправить событие в syslog» на странице
  настроек. UDP не шифруется: для передачи через недоверенные сети
  используйте локальный rsyslog-релей с TLS-выходом — плагин шлёт
  на localhost, релей — в SIEM.
- Ротация: `audit.maxBytes` (по умолчанию 5 МБ) → `.1`, старые сдвигаются,
  не более `audit.maxFiles` файлов (по умолчанию 5).
- Проверка: `./releng/verify-audit.py` (код 0 — цепочка валидна) или кнопка
  «Проверить целостность журнала» на странице настроек (проверяет текущий
  и ротированные файлы).

Правка выделения ИИ фиксируется событиями `ai_edit`: `decision` — `applied`
(применено), `canceled` (отменено), `chat` (ушло в чат), `error`; в `detail` —
режимы `preview|direct` и `diff|full`, размеры фрагмента и результата, число
замен и инструкция одной строкой (до 160 символов). Сам выделенный текст
и ответ модели в журнал **не записываются**; отключение — `edit.audit=false`.

Ограничения: журнал — обычный файл, его можно удалить (тогда проверка просто
не найдёт записей), цепочка продолжается от последней записи; аудит не защищает
от root. Смысл аудита — достоверная память о том, **что выполнялось**, а не
защита журнала от уничтожения (для этого нужен внешний сбор логов).

## 6. Что остаётся на пользователе

- Проверять содержимое карточки подтверждения (какой SQL выполняется).
- Просматривать предпросмотр правки (`Ctrl+Alt+E`) — точечные замены
  с подсветкой «было/стало» — перед «Применить»: модель может ошибиться;
  ненужную замену можно снять галочкой, отмена — Esc или один `Ctrl+Z`.
- Не включать «Allow always» для `db_executeSql` на продуктивных подключениях.
- Использовать для прода учётные записи СУБД с минимальными правами: даже
  при профиле `FULL` нельзя сделать больше, чем позволяет роль.
- Периодически проверять журнал аудита и целостность цепочки.

## 7. Сообщение о проблеме безопасности

Найденную уязвимость не публикуйте в открытых трекерах — сообщите владельцу
репозитория (см. историю git / сопроводительную документацию организацией).
Полезно приложить: версию плагина (`dist/BUILD-INFO.txt`), версию DBeaver,
сценарий воспроизведения и фрагмент журнала аудита.

## 8. Корпоративная политика администратора (1.5.0)

Источник политики (по приоритету):

1. системное свойство `-Daisql.enterprise.policy=/etc/dbeaver/ai-sql-enterprise.properties`
   (добавляется в `dbeaver.ini`; файл размещается вне досягаемости
   пользователя, чтение — только root/ИБ);
2. файл `ai-sql-enterprise.properties` в каталоге настроек плагина
   (проще, но защищён только правами на каталог рабочей области).

Формат — те же ключи, что и в `ai-sql-plugin.properties`; значения политики
**перекрывают** пользовательские. Пример «банка»:

```properties
# Прод не трогать: профиль только для чтения на все продуктивные подключения
policy.profile.prod-*=READ_ONLY
policy.defaultProfile=STANDARD
# Запрещённые конструкции действуют всегда (кроме FULL, который тоже запрещён)
policy.forbidden=DROP\\s+TABLE;\\nTRUNCATE\\s+;\\nALTER\\s+SYSTEM;\\nDROP\\s+DATABASE
# Маскирование и детекция ПДн обязательны
mask.enabled=true
mask.rules=*.password=***; *.token=***; *.secret=***; *.email=***@***; *.phone=[телефон]
mask.detectPII=true
# Инъекции: строгий режим, данные из БД помечаются
injection.mode=strict
toolOutput.fence=true
# Аудит обязателен и уходит в SIEM
audit.enabled=true
audit.redactLiterals=true
audit.syslog.enabled=true
audit.syslog.host=syslog.corp.example
audit.syslog.port=514
# Изменяющие инструменты отключены полностью
tools.disabled=executeSql,runMacro,defineMacro,deleteMacro
```

Поведение:

- **Fail-closed**: если политика задана системным свойством, но не читается
  (удалена, нет прав, битая кодировка), все инструменты плагина отказывают
  в работе с понятной ошибкой. «Нет политики» не должно молча превращаться
  в «всё разрешено».
- Отказы по политике видны в аудите (`decision=deny`,
  `detail=enterprise policy…`) и в SIEM с severity warning.
- На странице настроек зафиксированные поля недоступны для редактирования,
  вверху — строка «КОРПОРАТИВНАЯ ПОЛИТИКА АКТИВНА» с перечнем ключей.
- `db_getContext` показывает статус политики модели.
- Пользовательская запись в `ai-sql-plugin.properties` не может ослабить
  зафиксированные ключи; файл политики перечитывается без перезапуска.

## 9. Секреты, сеть и TLS

- **Плагин не хранит секретов**: API-ключи и токены ИИ-провайдеров
  принадлежат DBeaver и хранятся в его защищённом хранилище
  (Preferences → AI). В файлах плагина (`ai-sql-plugin.properties`,
  политика, макросы, аудит, `ai-sql-session.id`) секретов нет;
  права на них — `0600` (владелец), устанавливаются автоматически (POSIX).
- Корпоративная выдача ключей: настройте ИИ-профиль DBeaver на внутренний
  OpenAI-совместимый шлюз (Ollama, vLLM, LiteLLM, корпоративный прокси) —
  тогда ключи не покидают инфраструктуру. Переменные окружения и vault
  подхватывает сам DBeaver (26.3+).
- **Прокси и TLS-инспекция** (Zscaler/Netskope): сетевые настройки —
  штатные *Window → Preferences → General → Network Connections* DBeaver
  (Active Provider: Native/Manual, https-прокси, bypass-список);
  корпоративный корневой сертификат импортируется в JRE DBeaver
  (`keytool -importcert -keystore <dbeaver-jre>/lib/security/cacerts`).
  Плагин сетевых вызовов к модели не делает — всё через движок DBeaver;
  единственный собственный сетевой вызов — UDP-syslog (см. §5).
